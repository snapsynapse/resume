2026-09-09
- Extended target/company role-context routing so every application context is a data addition rather than a site rewrite. Each entry carries the source role, requisition metadata, a public-safe location answer, application-specific prompt context, and the evidence boundaries that keep the answer honest.
- The hero role line now leads with the applied-for title when an application context is active, so a reviewer arriving from a posting sees the role they are hiring for first, with the durable target titles following.
- Employer application presets left the public repository. They live in a private JSON loaded server-side from an environment variable; the repository carries the mechanism, the durable targets, a validator, and a fake fixture. The list of employers behind tailored links is no longer in source, history, or tests.
- Tailored links now read ?company=<key>&target=<target> (for and role are accepted aliases). A new read-only /api/role-context endpoint returns only the public-safe part of an entry (label, hero titles, suggested questions, source role, location context); the prompt delta never leaves the server, and an unknown key returns the same target-only context a typo would.
- Context is chosen only by the link the reader clicked. Referrer-based employer detection was removed.
- A visible hero notice names the tailored view and links to the neutral version in one click. The parameters are positioning selectors, not identifiers: not logged, not persisted, and stripped from the analytics page URL before any event leaves the browser.
- Default public artifacts (index.html, llms.txt, llms-full.txt, agents.json, resume.txt) still name no pursued employer and no applied-for role title. That regression check now runs against the fake fixture, and a reveal-resistant hash scan fails CI if any tracked file names a real one.
- The assistant guide now states that URL context parameters are reader-facing positioning selectors, not tracking identifiers. Guide version 2026.9.9.
