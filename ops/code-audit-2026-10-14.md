## A1: P1, tailored employer and role labels enter analytics
Locations: `src/components/AIChat.tsx:147`, `src/lib/role-context.ts:283`, `src/lib/analytics.ts:78`, `src/components/AIChat.test.tsx:102`.
When a visitor sends a chat message through a tailored link, `ai_chat_message_sent` includes `roleContext.label`. The composed label contains the employer and applied-for role. The analytics sanitizer removes query strings from selected URL fields but leaves this custom property intact. With analytics configured, that property can reach PostHog, contradicting the documented boundary that employer/context selections do not leave through analytics.
The offline component probe captured the invented employer/role label at `track`, then confirmed the actual sanitizer preserved it. An existing chat test explicitly expects the contextual label, so the current suite protects the wrong behavior. Historical production event contents were not inspected.
Recommended correction: omit this property or use a bounded public target key, and reject contextual labels at the telemetry boundary. Replace the existing expectation with a negative disclosure assertion.
Acceptance: submit a mocked tailored chat turn and verify the captured event and sanitized payload contain no employer key, employer label, source role, private context, or question text; permitted target metadata remains bounded.

## A3: P2, fit-result schema is declared but not validated at runtime
Locations: `api/analyze-fit.ts:294`, `src/components/FitAssessment.tsx:190`, `src/components/FitAssessment.tsx:360`.
The endpoint passes `fitSchema` to the provider but accepts any non-null object returned by `readFitResult`. The frontend casts JSON to `FitResult`, then dereferences `matches.length`, `matches.map`, and corresponding gap fields without validating them. A valid JSON response with the wrong shape can therefore cause a render failure instead of the intended structured boundary.
Offline provider mocks returned HTTP 200 for an empty object, an array, and an object with an unsupported verdict and invalid list fields. These tests exercise response handling without a live model.
Recommended correction: validate the complete response shape, enum, and nested field types before returning success; reject malformed data with the existing 502 boundary. Defensive client validation would also keep an unexpected response from breaking the page.
Acceptance: invalid objects, arrays, wrong verdicts, missing fields, and malformed match/gap items produce a structured error; a complete valid response still renders and updates the decision brief.
## A4: P2, JSON null crashes both POST handlers
Locations: `api/chat.ts:335`, `api/analyze-fit.ts:237`.
Both handlers guard JSON parsing but assume the parsed value is an object. A body containing JSON `null` parses successfully, then field access throws outside the provider error handler. With configuration gates satisfied, this becomes an unhandled server error instead of a documented 400 JSON boundary.
Both offline handler probes rejected with `TypeError` before invoking the mocked provider. This is not a provider failure or a prompt-semantic issue.
Recommended correction: treat parsed input as unknown and require a non-null, non-array object before accessing fields.
Acceptance: `null`, arrays, strings, numbers, and booleans return structured 400 responses from both endpoints; provider mocks remain uncalled; existing valid and malformed-JSON cases retain their behavior.
## A5: P2, stream disconnect handling watches the request lifecycle
Locations: `api/vercel-adapter.ts:87`, `api/vercel-adapter.ts:96`, `api/chat.ts:373`, `src/components/AIChat.tsx:92`.
The Node adapter subscribes to request `close` and `aborted`, while the response stream can outlive the completed request. In the real local HTTP probe, request completion occurred before the client cancelled its response reader. The response closed, but the server stream's cancellation hook never ran; the adapter consumed the later mock chunk as well. The existing disconnect test manually invokes a fake request-close callback and therefore misses this lifecycle difference.
A second compatibility probe with a pre-populated request body and a still-draining request showed the opposite failure: normal request completion cancelled the response and the client timed out. This is evidence about the adapter contract, not a claim that production currently reproduces that timing.
The browser chat fetch also has no AbortSignal or unmount cancellation, so closing the modal does not explicitly abandon its request. End-to-end cancellation needs transport and provider ownership to be tested together.
Recommended correction: detect response/socket disconnection, clean up listeners, propagate cancellation to provider work, and cancel the browser request on unmount. Preserve normal request completion and normal streamed EOF.
Acceptance: real local HTTP tests prove normal POST completion does not terminate a healthy response, client response cancellation stops upstream mock production promptly, and chat unmount aborts the in-flight request. A later production/model acceptance check remains separately held.
